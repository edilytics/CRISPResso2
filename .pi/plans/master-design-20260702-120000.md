# Design: Flat-Memory Adaptive Storage for Long-Read CRISPResso

Generated by /office-hours on 2026-07-02
Branch: master
Status: APPROVED

## Problem Statement

CRISPResso2 cannot complete analysis on long-read (PacBio HiFi / Nanopore) amplicon
data. Reads of multiple kilobases — and high per-read diversity — cause the pipeline
to consume unbounded memory and OOM. Users' only recourse today is to give up.

The goal is **flat peak memory across arbitrary input sizes**, delivered behind a
flag so the current path remains a parity oracle, with **byte-for-byte result
parity** (allele frequency TSV, count vectors, plots).

## What Makes This Cool

A bioinformatics pipeline that adapts: small datasets run fully in memory (fast),
large datasets spill to columnar parquet and stream (slower but *finishes*). Peak
RSS stays flat as reads scale. As a bonus, the allele table becomes a persisted
parquet artifact users can re-open in a notebook or re-plot without re-running
alignment.

## Current State

Three layered in-memory structures hold the same data, each capable of OOM-ing
long reads:

1. **`variantCache` (raw-read dedup dict)** — `CRISPRessoCORE.py` ~line 1325.
   While reading FASTQ, every unique R1+R2 concatenation is stored as a key (long
   string) with `[count, quals]`. For long reads diversity is ~1:1, so this dict of
   long strings is a memory ceiling *before alignment even starts*.

2. **`variantCache` (re-materialized payloads)** — `CRISPRessoCORE.py` ~line 1380.
   Workers write `variants_{i}.tsv` (one line per unique read: `seq\t{json}`).
   The JSON encoder (`CRISPRessoShared.CRISPRessoJSONEncoder`, ~line 812)
   serializes each numpy array via `.tolist()` → JSON text. The parent reads every
   line back and `json.loads()`-es *all of it into RAM at once*, rebuilding full
   payloads (strings + ~10 numpy arrays of amplicon length each) into `variantCache`.

3. **`alleles_list` / `df_alleles`** — `CRISPRessoCORE.py` ~line 4298. A *second*
   copy of most of the payload, reshaped into a pandas DataFrame with object-dtype
   array columns. Consumed by ~30 plot functions (`plots/data_prep.py`) via
   `iterrows`/`groupby`/`to_csv`, and by VCF/report writers.

Key observation: **disk spillage already exists** (workers write `variants_{i}.tsv`).
The OOM is from *eager re-materialization* on read-back, plus the raw-read dedup
dict, plus df_alleles. Parquet-izing df_alleles alone leaves ceilings #1 and #2
intact.

## Constraints

- **Python 3 only; numpy < 2** (compile-time constraint on Cython modules).
- **Cython modules** (`CRISPResso2Align.pyx`, `CRISPRessoCOREResources.pyx`) are the
  alignment engine and payload builder — they stay as-is; they emit numpy arrays.
- **Result parity is mandatory** — allele TSV, count vectors, plots must match the
  current path. This is the acceptance test.
- **Flag-gated** — new path runs alongside the current path until validated.
- **Plots stay pandas** — premise #4: plots receive pandas DataFrames materialized
  from parquet *slices*, not the whole frame. ~30 functions in `plots/data_prep.py`
  and `CRISPRessoCORE.py` use `df_alleles` via iterrows/groupby.
- **New dependency**: polars (with pyarrow/parquet). Not currently in `pyproject.toml`.

## Premises

1. The memory ceiling is set by holding one copy of every unique read's alignment
   payload in RAM simultaneously — first inside `variantCache`, then again as
   `df_alleles`. Parquet-izing `df_alleles` alone leaves the `variantCache` ceiling
   intact and will NOT prevent OOM on long reads. ✓ agreed
2. The worker→parent IPC is already disk-spilled; the fix is making read-back
   lazy/streaming and the on-disk format columnar (parquet/arrow) so arrays are
   native, not JSON `.tolist()`. One move eliminates JSON cost, re-materialization,
   and makes `df_alleles` a lazy view. ✓ agreed
3. Flat memory across arbitrary sizes requires a streaming aggregation for allele
   dedup (group unique `aln_seq`, sum `#Reads`) that can spill — an OLAP engine
   (polars streaming) must own the dedup, not an in-RAM dict. For small inputs it
   stays in memory (the "spectrum"). ✓ agreed
4. Plot code is the largest blast radius. Parity is achievable WITHOUT rewriting
   plots to polars idiom — give each plot a pandas DataFrame materialized from a
   parquet *slice*. ✓ agreed
5. Result parity = identical allele frequency TSV, identical count vectors,
   identical plots (pixel-diff allowed for nondeterminism). New path gated behind
   a flag; current pandas path stays as parity oracle. ✓ agreed

## Approaches Considered

### Approach A: "Lazy read-back" (minimal viable)
Keep `variantCache` and the FASTQ dedup dict as-is. Only fix the two eager
materializations: workers write parquet instead of JSON-TSV; parent reads back
lazily in chunks; `df_alleles` written to parquet and consumed as lazy slices by
plots. No streaming dedup — relies on raw-read dedup fitting in memory.
- Effort: M. Risk: Low.
- Pros: ships fastest; plot code untouched beyond slice extraction.
- Cons: **fails premise #1/#3** — if the FASTQ dedup dict OOMs (long reads, high
  diversity), still dies. Only defers the ceiling. Rejected for this reason.

### Approach B: "VariantStore abstraction + polars streaming" (ideal) ✓ CHOSEN
Introduce a storage layer owning read→align→collapse. Raw reads counted via polars
streaming `group_by` that spills when cardinality exceeds a threshold. Workers
append aligned payloads to parquet. Streaming `group_by` on `aln_seq` +
reverse-complement-equivalence does the post-alignment collapse. `df_alleles`
becomes a lazy parquet scan; plots receive pandas DataFrames materialized from
filtered slices.

### Approach C: "DuckDB as single query engine" (lateral)
Replace `variantCache` and `df_alleles` with DuckDB tables on parquet; DuckDB owns
both dedup stages and slicing; plots call DuckDB → arrow → pandas. The post-
alignment pipeline becomes SQL queries.
- Effort: L. Risk: Med-High.
- Pros: one engine; streaming aggregation battle-tested; interactive queries.
- Cons: SQL rewrite of imperative aggregation/count-vector logic (paradigm shift);
  plot blast radius unless arrow→pandas at boundary. No marginal benefit over B
  unless polars streaming proves unable to handle long string columns — in which
  case DuckDB is the fallback for that one operation.

## Recommended Approach

**Approach B.** It is the only option that meets the stated bar (flat memory across
arbitrary sizes) with the desired "spectrum" behavior (in-mem when small, spill when
large). The hardest sub-problem — streaming reverse-complement dedup — has a known
shape (canonical key `min(seq, rc(seq))`) and is a boilable task. DuckDB (Approach
C) is the documented fallback for the RC-dedup operation if polars streaming cannot
handle multi-kb string columns without falling back to eager execution.

## Architecture (Approach B)

### New component: `VariantStore`

A storage abstraction (new module, e.g. `CRISPResso2/storage.py`) that owns the
read→align→collapse lifecycle and presents a lazy interface to consumers.
Internally adaptive: in-memory for small inputs, parquet-spilling for large.

**Responsibilities:**

1. **Raw-read counting (streaming, spill-capable).**
   - Input: streaming reads from FASTQ.
   - Operation: `group_by(read_key).len()` via polars streaming engine.
   - The read_key is the R1+R2 concatenation (current behavior). For long reads
     this collapses poorly, but the *streaming group_by itself* spills to disk
     rather than holding all keys in a dict — so peak memory is bounded by the
     streaming engine's chunk size, not by read count.
   - Quality arrays: stored alongside only when `args.fastq_output` needs them;
     otherwise dropped (current path stores them unconditionally — a latent waste).
   - Threshold: if estimated unique-read count × avg read length < `MEM_BUDGET`,
     stay fully in memory (polars eager); else streaming. This is the "spectrum."

2. **Aligned-payload storage (parquet, columnar).**
   - Workers (existing `variant_file_generator_process` model) align their slice
     of reads and **append** rows to a shared/partitioned parquet file instead of
     writing `variants_{i}.tsv` JSON lines.
   - Columns: the fields currently in `get_allele_row` payloads — `aln_seq`,
     `aln_ref`, `ref_positions`, `all_insertion_positions`, `all_deletion_positions`,
     `all_substitution_positions`, `insertion_coordinates`, `insertion_sizes`,
     `deletion_coordinates`, `deletion_sizes`, `substitution_values`, plus
     `best_match_score`, `aln_ref_names`, `aln_scores`, `classification`,
     `count` (carried from the raw-read count), `caching_is_ok`.
   - Numpy arrays become arrow list columns (native, zero-copy, no JSON `.tolist()`).
   - Each worker writes its own parquet shard (one shard per worker, matching
     today's `variants_{i}.tsv` model — simplest concurrency, no inter-worker
     locking); the store concatenates lazily via a polars `scan_parquet` over
     the shard glob.

3. **Post-alignment collapse (streaming group_by) — three distinct stages.**
   The current code performs three separate merges; the store must preserve
   their distinct semantics, all expressed as streaming `group_by`/joins:
   - **Stage 3a — `aln_seq` re-key** (~line 1441): reads keyed by raw R1+R2
     concat are re-keyed by their aligned `aln_seq`, merging `count`. This
     collapses reads that differed as raw input but aligned identically.
   - **Stage 3b — reverse-complement merge** (~line 3972): compute a canonical
     key `min(seq, rc(seq))` as a column, then `group_by(canonical_key)` summing
     `count` and keeping the representative payload (the `+` strand seq, matching
     current tie-breaking). This is the one extra string pass; it is streaming.
   - **Stage 3c — multi-reference fan-out** (~line 3992, `get_allele_row` per
     `aln_ref_names`): a read aligning to N references produces N allele rows.
     This is an `explode` on `aln_ref_names`, not a merge — expressed as a lazy
     explode + per-row payload selection.
   - `re_aln` reads (`caching_is_ok == False`, ~line 1398) are handled by
     re-aligning individually and appending — they do not participate in the
     streaming collapse (they are low-volume by nature).

4. **`df_alleles` as a lazy view.**
   - What was `pd.DataFrame(alleles_list)` becomes a polars `LazyFrame` scan over
     the collapsed parquet, with the `%Reads`, `n_deleted/inserted/mutated` casts,
     and sort expressed as lazy expressions.
   - Consumers that need the *whole* table (allele-frequency TSV write, VCF writer)
     stream it out via `sink_csv` / arrow batch writes — never materialized.
   - Consumers that need a *slice* (plots) call a `get_slice(ref_name, ...)` API
     that returns a pandas DataFrame filtered and collected from the LazyFrame.

### Consumer adaptation (plots stay pandas)

`plots/data_prep.py` and `CRISPRessoCORE.py` plot callsites (~30 sites) currently
take `df_alleles` and do `df_alleles.loc[df_alleles['Reference_Name'] == ref]`,
`iterrows()`, `groupby(...)`, `str.find(...)`, etc. These stay **unchanged** — they
receive a pandas DataFrame. The only change is *where that DataFrame comes from*:
a filtered+collected slice from the parquet LazyFrame, rather than a slice of the
whole in-RAM frame. This is the key to keeping blast radius low (premise #4).

### Count vectors / class_counts (imperative aggregation)

The per-reference count vectors (`all_insertion_count_vectors`, etc.) and
`class_counts` are currently built by iterating `variantCache` payload arrays
(~line 4015+). Under Approach B these are built by a **streaming pass** over the
collapsed parquet: scan → for each batch, add `count`-weighted contributions to the
numpy accumulator vectors (same arithmetic, just batched). Outputs are identical
arrays. This is the second stream-out point (alongside TSV/VCF).

**Note on accumulator memory:** the vectors themselves are O(amplicon_length ×
num_refs × num_base_types). For a 10 kb amplicon with a handful of references this
is tens of MB — far smaller than per-read storage, but not zero. For pathological
cases (many references × very long amplicon) these accumulators could themselves
be non-trivial; they are a known, bounded, lower-order term and not addressed by
this design (out of scope — they are not the OOM driver for typical long-read
amplicon counts).

### Flag gating

- New arg, e.g. `--storage_backend` (values: `pandas` [default, current], `parquet`
  [new]) or auto-select. Auto-select is a follow-up; first cut is explicit.
- The current `pandas` path is untouched and serves as the parity oracle in tests.
- Downstream tools (Batch, Pooled, WGS, Compare, Aggregate) call into the same
  `CRISPRessoCORE.main` — they inherit the flag for free.

## Open Questions

1. **Polars streaming with multi-kb string columns.** Does polars' streaming engine
   spill correctly on `aln_seq` columns of 1–10 kb, or does it fall back to eager?
   *Resolution: spike first (see Next Steps #1). Fallback: DuckDB for this op.*
2. **Worker parquet shard schema uniformity.** All worker shards must share an
   identical schema (including when `write_detailed_allele_table` / `vcf_output`
   toggle extra columns) so `scan_parquet` over the glob concats cleanly. Resolved
   by deriving the schema once in the parent and passing it to each worker.
3. **`fastq_output` / `bam_output` paths** read `variantCache` payloads directly
   (~line 2263) for per-read annotations. Under the new path these need to scan the
   aligned-payload parquet joined to the raw-read count — confirm the annotation
   fields are all present in the stored schema.
4. **CRISPRessoBatch/Pooled/WGS** — do they have their own `variantCache`-equivalents
   that need the same treatment, or do they delegate to `CRISPRessoCORE`? (Initial
   scan suggests they delegate; verify before claiming scope.)
5. **Polars + numpy<2 compatibility.** Confirm polars version pinning plays nice
   with the numpy<2 compile constraint.
6. **Canonical-key memory for RC dedup (Stage 3b).** `min(seq, rc(seq))` adds a
   string column equal in size to `aln_seq`; in streaming mode this is per-batch,
   not whole-store, so bounded — but verify the streaming engine does not
   materialize the canonical column eagerly before grouping.

## Success Criteria

1. **Flat memory:** peak RSS does not increase as read count scales (measured at
   10k, 100k, 1M reads on a fixed amplicon). Target: peak RSS within a small
   constant factor regardless of input size.
2. **Long-read completion:** a PacBio/Nanopore amplicon run that OOMs today
   completes end-to-end under `--storage_backend parquet`.
3. **Result parity:** allele-frequency TSV, count vectors, and plot data identical
   to the `--storage_backend pandas` path on a suite of test amplicons (short + long,
   single + multiple references, with/without prime editing / base editing).
4. **Spectrum behavior:** small datasets run fully in memory with no measurable
   slowdown vs. the current path (within 10%).
5. **No regressions:** existing unit tests (`tests/unit_tests/`) and integration
   tests (`make all test`) pass under both backends.

## Engineering Review (2026-07-02)

### Scope finding (verified against code)

**Open Question #4 is RESOLVED.** CRISPRessoBatch / Pooled / WGS invoke the core
tool as a **subprocess CLI** (`CRISPRessoMultiProcessing.run_crispresso_cmds`),
not as an in-process call. They build command strings and shell out. Therefore the
`--storage_backend` flag passes through automatically and these tools require **no
changes**. Scope is confined to `CRISPRessoCORE.py` + new `storage.py` module.

**Important gap surfaced:** the design doc named only `process_paired_fastq`, but
verified that **all three** read-processing entry points share the same worker:

| Entry point | Worker | IPC file |
|-------------|--------|----------|
| `process_paired_fastq` (~1245) | `variant_file_generator_process` | `variants_{i}.tsv` |
| `process_fastq` (~1735, default single-read) | `variant_file_generator_process` | `variants_{i}.tsv` |
| `process_bam` (~2003, bam_input) | `variant_file_generator_process` | `variants_{i}.tsv` |

Because they share `variant_file_generator_process`, the worker-parquet-writer
change is made **once** and covers all three. The read-back merge logic differs
per entry point (paired has `re_aln` re-alignment loop; single & bam do not), so
the read-back layer of `VariantStore` must parameterize per entry point — but the
worker writer and the schema are shared.

Validation points: (V1) read_key non-empty check at FASTQ boundary;
(V2) shard schema validated against parent-derived schema on scan;
(V3) N_TOTAL==0 guard before Stage 3; (V4) parity diff at test boundary.

Concurrency concerns: Stage 2 — N workers writing N shards concurrently
(one shard each, no shared mutable state, matches today). Stage 1 & 3 are
single-process streaming; no concurrency.

External-dependency failure modes: polars/pyarrow must be importable (new
dep — fail-fast import check at CLI startup with actionable message).

```

                  └────┬─────┘
            read_counts.parquet written
                       ▼
                  ┌──────────┐
                  │ ALIGNED  │ ◀── workers join; each shard closed
                  └────┬─────┘
            shards/aligned_{i}.parquet written
                       ▼
                  ┌──────────┐
                  │ COLLAPSE │ ──3a→3b→3c──▶ collapsed.allele.parquet

                       ▼
                  ┌──────────┐
```

### Edge Cases Identified

22 edge cases identified, 22 with mitigations.

| # | Edge Case | Impact | Probability | Mitigation |
|---|-----------|--------|-------------|------------|
| 1 | Empty FASTQ (0 reads) | NoReadsAlignedException path; must match pandas backend | High (common) | Guard at Stage 1 end: if N_TOTAL==0 raise same exception as today (~line 4293); parity test covers |
| 2 | Single read in file | boundary on group_by; polars handles but verify count==1 | Med | P1 unit test: single-read FASTQ through both backends, diff |
| 3 | All reads unaligned (best_match_score<=0) | collapsed parquet empty; df_alleles 0 rows | Med | Stage 3 emits empty parquet; downstream already handles empty df_alleles today — verify, P1 test |
| 4 | Read with empty aln_seq (inserted as '' key today, ~line 3755) | canonical_key computation on '' — rc('')='' — fine, but min('','')='' | Low | P2 test: empty-seq cache entry round-trips; confirm count=0 sentinel preserved |
| 5 | Worker crash mid-shard | truncated parquet shard → scan_parquet fails or returns partial | Low | Parent validates each shard opens + row-count > 0 after join; on failure raise OutputFolderIncompleteException (same contract as missing variants_{i}.tsv today) |

### Known latent parity risks (surfaced by PR 7 wiring, to resolve in PR 8)

These do NOT affect the basic test (the PR 7 gate) but will surface when the
PR 8 parity suite exercises the corresponding paths:

1. **Detailed allele TSV array formatting.** PR 6's `write_allele_frequency_table`
   sink formats position/size arrays as numpy str (``[0 1 2]``, no commas) via
   `_to_np_int_array`. But the real pandas ``df_alleles.to_csv()`` formats them
   as **Python list** str (``[0, 1, 2]``, with commas) — because
   ``find_indels_substitutions`` (``CRISPRessoCOREResources.pyx``) emits lists
   (``ref_positions=[]`` + ``.append``), not numpy. The basic test uses the
   non-detailed projection (``crispresso2Cols``, no array columns) so this is
   unexercised; a detailed-TSV parity test (``--write_detailed_allele_table``)
   will fail byte-for-byte. Fix: the sink should format array cells as
   ``str(list)`` (commas) to match pandas, OR document the divergence.

2. **Homology RC-pair count semantics.** ``Alleles_homology_scores.txt`` is
   byte-diffed. The pandas path builds homology from ``variantCache`` *after*
   the 3b RC-merge, so a folded-away RC partner appears as a row with
   ``count = 0``. The parquet backend's
   ``compute_aln_stats_and_homology_from_shards`` builds homology from the
   **pre-merge** shards (both RC partners carry their original non-zero
   counts). These differ whenever the input contains reverse-complement read
   pairs. The basic test (FANC.Cas9) has no RC pairs, so it passes; a dataset
   with RC pairs will mismatch. Fix: persist the post-RC-merge variant store
   (one row per unique aligned read, folded count + ``aln_scores``) as a
   parquet during collapse — collapse already builds this store internally
   (``_collapse_rekey_and_rcmerge``); homology scans THAT instead of the shards.
   (This is the same artifact the deferred OQ-E3 parquet output would expose.)

3. **Scope guards.** PR 7's wiring raises ``BadParameterException`` under the
   parquet backend for ``bam_input`` / ``crispresso_merge`` / ``fastq_output`` /
   ``bam_output`` / HDR / prime-editing re-alignment. These paths must be wired
   (or explicitly deferred) before PR 8's parity suite can run them. See the
   PR 7 scope notes in ``CRISPRessoCORE.main``.
